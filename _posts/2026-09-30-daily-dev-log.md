## Today's Plan

Wednesday. The agent auth audit has been absorbing an enormous amount of energy — yesterday I closed a huge batch of items across that feature set, many of which weren't even on the plan. The privacy category work is still carrying a long tail of in-progress items, and the synthetic scenario actor audit has five items left that need deliberate attention rather than reactive visits.

### Main Focus

**Resolve `aa-decision-admitted-dispatch`, `aa-decision-idempotent-steps`, and `aa-decision-effect-dedup` as a sequenced unit** — These three are in Ready to Start and have a strict internal ordering. Dispatch should only occur after admission is confirmed; idempotency guards should be in place before any dispatch can be retried; deduplication of downstream effects depends on the idempotency guarantees being real rather than aspirational. If I work these out of order I'll write deduplication logic against a dispatch surface that still accepts unadmitted requests — that's the kind of error that looks fine in tests but fails in production under partial failures. The audit plan is explicit that each suspected bypass needs focused tests before the item closes, so none of these are documentation tasks.

**Close `aa-decision-reconcile` and `aa-decision-revocation` before touching `aa-test-decision-final`** — The reconciliation item handles failed decision effects; revocation invalidates queued decisions when authority is withdrawn. `aa-test-decision-final` proves async race and failure safety — which is exactly the failure mode these two items are designed to prevent. Writing the test first would mean I'm testing a surface that hasn't been hardened yet. The audit was identified as having 27 of 61 units done, with F-01 and F-04 as the remaining immediate containment targets. I want this decision pipeline fully locked before the final test suite runs.

**Advance `w4-effect-containment` and `w6-authorization-parity` in the synthetic scenario actor audit** — These have been active for the last 24 hours and both represent correctness claims, not polish. Effect containment (`w4-effect-containment`) proves the scenario doesn't produce real external side effects — that's a hard behavioral guarantee, not a soft one. Authorization parity (`w6-authorization-parity`) proves the synthetic actor goes through the same authorization stack as an ordinary principal. The scenario audit's current browser completion record shows both are still open despite significant work this week. The trade-off on `w6-authorization-parity` is whether to prove parity at the middleware layer or at the policy evaluation layer — I'm leaning toward policy evaluation because middleware can be bypassed by alternative request paths, but that's the decision I need to settle before I can write the proof.

**Move `col-6038-runtime-compatibility` from Ready to Start into the active build** — This is the one remaining ready item in the privacy category management work: enforce the approved compatible read policy at runtime. It's a natural next step after the impact preview work that landed yesterday (PR #6516). I've been heads-down on the COL-6038 branch for six days, and the runtime compatibility policy is the constraint that makes the whole catalog activation story coherent — without it, an approved category version can be read against an incompatible runtime configuration. The enforcement logic needs to sit at the resolver level, not the API boundary, because the resolver is the only layer that has temporal determination context.

## Today's Update

September 30th turned into a day of closing surface area across almost every active system simultaneously — not because the plan called for it, but because several feature sets had been sitting at the edge of closure long enough that finishing them in parallel was the more coherent choice than sequencing them artificially.

The codebase maturity work was the structural anchor. I completed both CM-01 (tenant booking list) and CM-02 (billing account identity) in full, and moved deep into CM-03 (billing read consoles) before day's end. The booking list refactor is the clearest example of what this maturity effort is actually doing: the `BookingController::index` method was doing its own filter normalization inline, which meant any caller had to understand the controller's internal conventions to get consistent results. Moving that normalization behind a proper Porto Action means the interface is now the contract — callers pass structured intent, the Action handles normalization, and the controller becomes a thin delegation point. I characterized pagination, filters, tenant isolation, and telemetry before touching any implementation, which gave me regression gates that were already failing before I changed a line of business logic. That ordering matters: characterization tests written against the old behavior are the only honest measure of whether the new implementation is equivalent.

CM-02 was more surgical. The billing account identity correction replaced a User-based account selection path that had been treating user identity and billing account identity as interchangeable — they're not, and the legacy cost dashboard was the most visible place that conflation lived. I mapped authorized Billing Account visibility explicitly, added a regression that holds the User-versus-BillingAccount identity distinction, validated the selected account input at the request boundary, and then bound all billing reads to the authorized account rather than the ambient user. The view label alignment was the last piece; it's the kind of fix that seems cosmetic but actually closes an ambiguity in what the UI is claiming to show. CM-02's closeout decision was interesting: the legacy cost dashboard didn't just get corrected, it got removed entirely as an unused path. That's a judgment call I'm comfortable with — carrying dead views that reference the wrong identity model is worse than the temporary loss of the feature, especially before any real operators are using it.

The privacy work was the most sprawling. Fourteen items across the privacy feature set, covering stored determination comparisons, principal-tenant projection digest verification, consent grant binding at admission, policy decision replay, and a handful of fixes to the evidence and rollback report contracts. The piece I keep returning to is the projection digest comparison — I'm comparing principal and tenant projections to prove stored determination parity, which is only meaningful if the comparison itself is consistent. That meant locking the stored determination comparisons in a specific, reproducible sequence rather than letting evaluation order vary. Whether that lock belongs at the query layer or in the domain object is a question I made a call on (domain object, so it's testable without a schema dependency), but I wouldn't be surprised if that decision needs revisiting once the admission composer sees heavier use. The admission composer resolution through the container is now in place, which cleans up a test coupling issue that had been making some of the optional choice admission proofs harder to write than they should've been.

The decision system, scenarios, and trust feature sets got meaningful coverage too. For decisions specifically, the authority revocation path needed to persist in-flight — meaning if authority is revoked while a dispatch is already running, that revocation has to survive rather than being swallowed by the completion path. Alongside that, I added rollback rejection after evidence exists and stopped forward retry on authorized rollback. Those two constraints interact: once rollback evidence is recorded, replay should be rejected, and the retry path shouldn't be able to route around that by re-entering the forward path. The scenarios work covered the queued support change denial surface in detail, including dead letter binding to ticket owner — that's the kind of edge that only matters once the queue infrastructure is running real traffic, but closing it now means future debugging has a known ownership boundary to start from. The payment gateway work consolidated the Stripe Connect readiness rule: re-read operations now share a single readiness derivation rather than each caller implementing its own interpretation of the `account.updated` event shape.

CM-03 is still in progress — rate console characterization, the Action implementation, controller delegation, and gates are all started but not closed. That's the carryover. The read contract and cost extraction reconciliation are the two items I want to close first tomorrow, because the gate run depends on both of them being stable before it means anything.
