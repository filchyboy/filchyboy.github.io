## Today's Update

Two thin vertical slices crossed the finish line today, and the volume of supporting work that went alongside them was larger than I'd anticipated when the day started.

The bigger of the two was the ProductSurface ESR compiler baseline parity slice (tv697). I worked through the full sequence: contract scope baseline, backend orchestration for the compiler adapter, affiliate baseline schema for data determinism, API contract hardening for compiled runtime metadata, frontend integration for the compiled affiliate preview, observability instrumentation, quality gates, review remediation for the consumer/owner contract, and accessibility coverage. The piece I want to call out specifically is exposing the active schema and form version IDs on both runtime and submission — that's a concrete data determinism guarantee that prevents the compiled baseline from silently drifting relative to the schema the consumer was actually shown. Without it, the runtime contract can claim parity with a schema version that's already been superseded. The other notable decision was marking the compiler adapter methods with `#[Override]` — that's a PHP 8.3 attribute, and the reason it matters here is that the adapter implements an interface contract that will eventually have multiple concrete implementations. Marking the overrides explicitly means a future implementor can't silently drop a method and have it compile clean.

The agent surface action log review loop (tv678) ran in parallel and completed the same full sequence. The distinct work here was instrumenting `agent_surface.action_log` telemetry — wiring up the telemetry events that future observability tooling will read when reviewing what actions agents took on a given surface. The data determinism and API contract hardening passes for action logs are also establishing what shape the log records will take before any consumer code is written against them, which is the right order: consumers shouldn't have to negotiate with a schema that was defined after they were built.

Alongside those two slices, a cluster of cross-cutting work accumulated. The routing area got a duplicate route name ratchet with a baseline, a duplicate route method/path tuple ratchet, and a reconciliation of surface ownership against actual consumers — three separate enforcement points that together make it harder for the route registry to drift into ambiguous state as more surfaces are added. The sync work retired unreachable admin `revoke-token` and `remote-wipe` routes and aligned the retired contracts with documented rationale; dead routes in an admin API aren't just noise, they're potential confusion surfaces during future security review. The token validator work added duplicate and conflict detection by full path, which is a natural companion to the routing ratchets — enforcing uniqueness at the route level and at the token validator level are solving the same class of problem from different angles.

The privacy work was the most scattered-looking set today, but there's a coherent thread through it: I was establishing the boundary conditions for how the engine handles source archives. Binding Desktop socket normalization to the original engine, accepting exact explicit IPv4 network defaults, recognizing the current private MySQL origin profile, bounding fresh archive input recheck work, handing off the live verified cold source archive, reusing the current builder source archive — these are all steps in fencing the archive pipeline so that the engine runner observes sources through a deterministic path rather than whatever happens to be resolvable at runtime. The one I'd flag as the most load-bearing is the admission observation through the original engine runner: that's the enforcement point that prevents a substituted engine from changing the semantics of what gets admitted. Getting it right now, before the archive pipeline is exercised in any real tenant workflow, is considerably cheaper than debugging it after the fact. I'm not fully settled on whether the `accept exact empty engine mount descriptors` behavior should be a hard rejection or a logged fallback — I went with acceptance for now, but that's a decision worth revisiting when the mount descriptor lifecycle is clearer.

The remaining items — a11y toast role derivation from variant, strict translation enforcement with schema version negotiation for the external agent surface, requiring owners for tenant registry projections, compliance showing exact scheme policy comparison values, and a handful of docs lint and dead link cleanup — were all genuine necessities rather than cosmetic tidying. The toast accessibility work in particular is one of those things that gets exponentially harder to retrofit once the component is used in fifteen places.
