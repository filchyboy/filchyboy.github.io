## Today's Update

Three capability feature sets crossed the finish line today — `cvg-002-capability-ownership`, `cvg-004-capability-cost-attribution`, and `cvg-006-capability-change-impact` — all in the same session. That's not typical, and it happened because all three were already deep into implementation. The remaining work in each was validation, UI wiring, and archive reconciliation, which meant I could move across them without losing the thread between transitions.

The ownership feature set (`cvg-002`) had the most interesting implementation surface. The core of it is a nomination-acceptance-decline state machine: one actor nominates a new owner, the candidate accepts or declines, and if neither happens within the window, the nomination expires. I built that as explicit transitions rather than inferring state from timestamp comparisons — the `decline` and `expiry` paths are first-class actions, not fallback conditions. That distinction matters because it gives the handoff history table a clean audit trail: every state change is a recorded event, not a reconstruction. The harder design question was the departure case (`cvg002-10`), where an owner leaves the platform without completing a handoff. I resolved that with a fallback boundary definition rather than trying to auto-assign — the system records the departure and marks the capability as unowned rather than silently promoting a secondary. Whether that's the right long-term answer I'm not certain about; it errs toward explicitness over convenience, which seems right for a capability that's supposed to have a named accountable party at all times. The UI work included rendering pending handoffs alongside current ownership status, and wiring the authorized deep-link paths so that nomination actions are reachable directly from context rather than requiring navigation to a separate management screen.

The cost attribution feature set (`cvg-004`) required the most careful sequencing. The allocation reconciliation logic (`cvg004-06`) and the idempotent supplier evidence confirmation (`cvg004-08`) had to be solid before any of the explanation rendering made sense — if the underlying allocation numbers aren't stable under repeated imports, the cost breakdown UI is just displaying noise. I built the native usage explanation and the external commitment explanation as separate composable pieces rather than a single unified view, which made the overlap statement (`cvg004-11`) cleaner: it has two well-defined inputs rather than pulling from a shared mutable blob. The external-to-native comparison render (`cvg004-16`) is the surface future operators will probably use most — it's the answer to "what would this cost us if we built it ourselves versus what we're paying a supplier for it." That rendering passed the financial statement reproduction test (`cvg004-17`), which was the gate I cared about most: given the same inputs, the output has to be byte-stable across runs. The post-review findings for `cvg004` also got addressed today; there were a handful of rounding edge cases in the allocation logic that the initial review surfaced, and those are closed.

The change impact feature set (`cvg006`) was the most dependency-heavy of the three. It reaches into ticket systems, source authority revision history, and queued work — which means the preview it produces can go stale if any of those inputs change between when the preview is generated and when a cutover actually happens. I handled that by persisting the impact preview as an immutable snapshot (`cvg006-08`) rather than computing it on demand at cutover time. The trade-off is storage against correctness: a live-computed view is always current but gives you no way to compare "what we said would happen" against "what actually happened." The snapshot approach gives you that comparison. Stale approval detection got instrumented (`cvg006-16`) so that when a preview is more than a threshold age, the UI surfaces a warning rather than silently showing potentially outdated dependency counts.

Outside the three capability sets, a handful of cross-cutting pieces landed: capability responsibility handoffs in the tenancy layer, an ownership allowlist constraint that prevents arbitrary capability assignment, a fix to skip departure success logging when no ownership state actually changed (that one was a noise-reduction fix — the log was firing on no-ops), and role guard differentiation on admin user forms. The demo operations dashboard got its initial routes, and the compliance layer now retries GPC visitor write deadlocks rather than failing the request. With the three capability feature sets archived and the billing and service layers updated to reflect them, the capability definition track is substantially more complete than it was this morning — which opens the implementation phase for anything that depends on knowing who owns what, what it costs, and what changes when you touch it.
