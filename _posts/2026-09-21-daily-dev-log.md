## Today's Update

Today was a closing day — not in the sense of wrapping things up neatly, but in the architectural sense of a long, multi-track effort reaching a defined terminal state. The Revyrie demo hardening and expansion work is done. All four parallel tracks are closed, the union quality gate sweep passed, the final readiness disposition is issued, and the plan is archived. That's the headline, and it's worth being direct about what it took to get there.

The four tracks were designed to be independent enough to run in parallel without constant coordination but interdependent enough that the integration step at the end actually means something. Track 1 handled the demo payment lane resolver — the `CheckoutPaymentLaneResolver` contract, `TenantMerchantAccountLaneResolver` implementation, the `demo_rehearsal_records` migration, and the full matrix disposition algorithm. The lane separation between real Stripe and the fake provider isn't cosmetic; it's the mechanism that lets future operators demonstrate payment flows without touching live credentials, and it has to be airtight at the tenant boundary. I wrote cross-tenant negative tests specifically because the failure mode there is not a crash — it's a demo that silently lets the wrong lane through and produces misleading evidence. The manifest determinism tests (`rdhe-t1-09`) exist for the same reason: if the runtime manifest isn't reproducible, you can't trust the evidence it produces.

Track 2 was the conversational commerce layer, and it's the track I'm least fully at peace with. The `RecognizeCommerceIntentTask`, `BuildCheckoutPurchasePreviewTask`, `PurchaseControl` model, `IssuePurchaseControlTask`, and `PurchaseControlRedemptionService` all exist and test correctly. The MySQL concurrent-confirmation race test (`rdhe-t2-26`) passes. What I'm genuinely uncertain about is whether the `AwaitingConfirmation` state surface is narrow enough — the state machine covers stale, altered, replayed, and expired controls, but the boundary between "awaiting" and "timed out" involves a judgment call about what counts as a stale request in a demo context versus what should block progression. I made a choice, documented it in ADR-0376 as an amendment, and moved on, but I wouldn't call that settled.

Track 3 covered the React layer: `useConversationalPurchase` hook, `PurchasePreviewCard` component, `MCPChatInterface` stale-request guard, and Cypress specs for all six matrix cells (BP-F, BP-S, CC-F, CC-S, operator continuation, and order fallback). The accessibility pass with `jest-axe` ran against both the chat interface and the preview card. Track 4 handled the remaining infrastructure — `customer_shipping_addresses` migration and `CustomerShippingAddress` resolver, `EmitAgentActionReceiptTask`, lazy expiry of overdue holds under the calendar lock, the `LocalDemoMessageCapture` component and its gating tests, and pulling the hardcoded Stripe Connect provider out of appointment confirmation in favor of the lane resolver. That last change (`rdhe-t4-16`) was the kind of thing that should have been done earlier in the track but kept getting deferred because the appointment path appeared to be working. It was technically working — just not correctly for the fake lane.

Layered on top of all of this was audit pass 12, which established the canonical repository state and runtime evidence, refreshed the cumulative audit package, ran the governed MCP payment probe, and captured browser evidence for Tier 1 checkout and denial flows. The plan accounting work — splitting, reconciling, archiving, and updating the version number — sounds administrative, but it matters: I now have a clean separation between what this cycle committed to and what carries forward. The September 23 demo has a defined, evidenced readiness state. What it doesn't have yet is the pressure test of an actual audience, and that's the only thing that will tell me whether the matrix disposition algorithm holds up when someone deviates from the script.
