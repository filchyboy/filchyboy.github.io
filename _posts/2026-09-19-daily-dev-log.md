## Today's Update

The last four days of work converged on a single question: is the September 23 Revyrie demo actually ready, or does it just look ready from a distance? Today was the answer — delivered in four overlapping audit passes, a full governed-booking-links demo track, and enough regression and quality gate coverage to have a defensible claim either way.

The governed-booking-links demo work was the most self-contained thread. I built it from the planning documents up: README and ticket details first, then the implementation plan and mutation contract, then the fixture seeding sequence — staff calendar, weekday availability, locked intake profile, and reusable comms policy. The fixture work matters because future operator demos can't depend on ambient data; they need a deterministic reset path that leaves the demo-tenant in an exact known state. I ran the full publish sequence for both the free and paid Governed Booking Links, added verify assertions covering both, and extended `OperatorDemoFixturesTest` to cover the appointment seed path. The feature test for fixture-published resolve and isolation confirms that demo fixtures cannot touch an unrelated BillingAccount — that property needs to be provable before anyone hands a demo to a real operator audience. The demo script itself is a 10-15 minute Instant Scheduling walkthrough, and the supporting runbook documents the local mail verification path and reset procedure with claim-safe wording. The whole thing closes with a cross-link to pass-4 C5 as the authorised successor, so the lineage is explicit.

The readiness audit work ran in three distinct passes today (P4, P5, and pass-3), and the discipline was necessary. P4 established canonical state and runtime topology, revalidated the audited SHA against the execution checkout, and verified live provider and payment-session responses after restart. The payment path work (P0-1) restored the primary checkout path; P0-2 made fixture seeding a mandatory preflight gate rather than an optional step someone might skip under time pressure; P0-3 retired false payment narration. I ran focused backend test files for the exact gates touched — payment retry and post-commit failure preserving exactly one result, competing callers and stale quote refusal, Orders list/detail/transition denying unrelated accounts. All of those are properties that need to be provable with a test artifact, not just claimed in a document. P5 then took the pass-4 findings and resolved the remaining P0 items: the authenticated 403 Return Home now points at `/checkout` rather than a dead end, `ForbiddenReturnHomeTest` is updated to cover that target, the checkout grand total now renders from quote subtotal plus selected shipping rate (not a fabricated number), and the fabricated `/admin/dashboard/orders` route is gated behind `role:super-admin` with stray links retargeted. The nginx change to allow `/.well-known/` before the dotfile deny rule was less obvious — that path needs to serve MCP discovery, and the prior deny rule was blocking it. I verified the 200/403 split after the change and ran MCP discovery regression tests to confirm nothing adjacent broke.

Pass-3 went deepest — it's where the Orders governance implementation actually lives. I added the lifecycle and replay evidence schema via migration, exposed lifecycle version and fingerprint metadata on the model, updated the detail endpoint to return the authoritative lifecycle version, and added a request contract requiring both the transition key and the expected lifecycle version. The fingerprinted replay binding (tying retries to exact governed input) and the locked-version transition enforcement together close the ABA problem: a delayed request that arrives after an intervening lifecycle change gets refused rather than silently applied. The uniqueness recovery path handles the case where two concurrent callers race to commit — the database winner is recovered rather than producing a duplicate event. I proved all of this in disposable MySQL with a race contenders test and a separate ABA-cycle test. The frontend side sends the selected lifecycle version and shares control/handler admission flags, so the UI has the information it needs to show the right affordances without polling for state.

The P2 items across all passes were real but clearly lower priority than the P0/P1 work: shipping-rate radio alignment on checkout, the compliance panel raw i18n key display, Stripe Connect error copy made channel-neutral, shipping_amount surfaced on the Orders detail panel, confirmation focus/scroll on success, and the duplicate `main` landmark on `/checkout`. I'm less certain whether the compliance panel fix is the right long-term approach — hiding it is expedient for the demo, but the underlying i18n gap will need a real resolution before this becomes a production path. On the other side of that, the channel-neutral Stripe error copy is genuinely the right fix regardless of the demo: the previous wording implied Stripe was the only payment provider, which isn't an accurate claim about the architecture. The week's output is captured in a September 13-19 weekly review package and source manifest, revised with provider and continuity evidence, which closes out the OI record for this period.
