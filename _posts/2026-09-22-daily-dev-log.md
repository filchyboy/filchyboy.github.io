## Today's Update

Today was a single-topic day, and a large one: closing remediation-6049, which was a systematic audit and rebuild of every authorization decision in the MCP routing layer. The work has been accumulating across multiple sessions, and today was the session where the remaining 87-plus units across the feature set reached a state I'm willing to call closed.

The spine of the work was the `AdmitMcpRouteAction` — a deep orchestration module that now owns the full admission sequence for any TOON-protected route. Before this, the responsibility was distributed across middleware in ways that made it hard to reason about what happened in what order. The admission module enforces a strict sequence: a valid, active Sanctum principal has to exist before anything else runs; token abilities are checked against the route declaration, not against whatever the caller happens to present; the route signature is bound to both the principal identity and the bearer token so the two can't be decoupled; graph, principal, and active tenant have to agree before the lookup proceeds; and class-level Gate authority runs before any resource-level policy is consulted. The ordering matters because failing at step one is cheaper than failing at step five, and the current structure makes the failure points explicit rather than emergent. Delegation identity and lifecycle revision validation is also in there as an optional check — it only runs when delegation context is present, but it runs before the lookup rather than after, which is where it should have been from the start.

The route authority matrix is the other artifact I'm treating as load-bearing. Every TOON-protected route now has complete authority metadata — principal requirements, source capability posture, mutation idempotency contracts, and replay semantics — and any route lacking that complete metadata fails closed at runtime. That fail-closed default is recorded explicitly in the schema rather than being an implicit side effect of a missing field, which is the distinction that matters when someone adds a new route six months from now and forgets to populate the metadata. The matrix covers the full surface: Commerce Checkout, Orders, ETL mutations, domain and publishing authority, Agent Interface compatibility, capability issuance and redemption, A2UI, Analytical Surface operations, Collision Engine, Compliance, FinOps, Provenance, alert and escalation paths, and the lower-risk read and report routes. Each of those got a characterization pass to identify what self-assertion or unauthorized reachability looked like before admission hardening, and each has a corresponding test suite that exercises principal isolation, tenant isolation, and the specific failure modes the characterization surfaced. The checkout tenant fallback removal deserves a separate mention — `MCP checkout handlers` previously accepted a caller-selected tenant as a fallback, which is exactly the kind of ambient authority that makes authorization audits unreliable. That fallback is gone.

I'm less certain about one architectural boundary: the split between `mcp.auth` middleware and `AdmitMcpRouteAction`. I've documented `mcp.auth` as handling metadata enrichment and rate limiting rather than authorization decisions, and the admission action handles everything that touches principal identity and authority. That division is defensible, but it requires discipline from future contributors to not let authorization logic creep back into `mcp.auth` because it's the obvious place to put a quick check. The rename-or-document unit was a documentation-only resolution, not a structural one, and I'm aware that documentation-only boundaries don't hold forever. I'll likely revisit whether those two concerns should be more explicitly separated at the type level before this becomes a production path that's hard to change.

The remediation set also produced a signed-grant test fixture using real keys rather than mock or entropy-shaped signatures, ADR-0258 was amended to document universal principal admission, and the route matrix and closure artifacts are reproducible rather than hand-maintained. The demo and chat feature sets got parallel attention: frame-free fake checkout evidence, saved-card UI and hash evidence, Stripe browser spec type-checking, and disabling chat controls during purchase confirmation loading. Dependencies were bumped across both Composer and npm groups, and the pre-push gate now scopes to pushed refs rather than running against everything. The remediation is archived. What the closed state enables is straightforward: future capability registrations have a defined process for entering the authority matrix with complete metadata, and the admission layer is a single place to audit rather than a distributed one.
