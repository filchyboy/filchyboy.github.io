## Today's Update

The headline for today is TV806 — the Event Recording to Publishing Handoff Loop — which went from contract baseline to full production extension evidence in a single session. That's a long distance to cover in one day, and the sequence mattered: I started with the contract scope baseline and backend orchestration, then locked data determinism before touching the API contract hardening. Doing those in order meant that when I admitted the production extension, I already had a stable data shape underneath it. The production trail ran all the way through: live destination profile admission, delivery manifest binding, private release request, private access revalidation at retrieval, attributable outcome recording, public media submission to Publishing, publication effect reconciliation, withdrawal and replacement, revision-bound live release intent coordination, uncertain live start/stop result reconciliation, and commercial obligation projection. That last one — projecting production commercial and service obligations — is the piece I'm least certain about in terms of long-term shape. The obligations model reflects what I know about the publishing contract today, but the specifics of commercial terms tend to shift as platform policy firms up. I'd rather have it modeled explicitly and wrong than unmodeled, but it's flagged.

The media and events work connected directly to TV806's publishing surface. On the media side, I established recording authorization with reviewed rights and recipient grants, preserved authority expiry instants, enforced recording scope and current recipient admission, reused owner verification when opening approved recordings, and cleaned native process and transaction state after failed schedules. The publication failure recovery work produced what I'm calling a portable native proof — a recoverable artifact from a failed publish that lets the system reconcile without requiring a full re-submission. Whether "portable" is the right property to bake in at this layer is still an open question; I may revisit this once the live intent reconciliation path gets exercised against real provider responses. On the events side, denying unverified recording authority simplified the handoff inputs considerably — the previous path was doing too much negotiation at the handoff boundary, and stripping that out tightened the contract.

The checkout and orders work ran in parallel with a clear dependency chain. On the checkout side, I measured the Orders customer snapshot source variant and merchant capability source dependencies before touching the address schema source evidence binding — that ordering kept the schema work grounded in what the snapshot actually needs rather than what I imagined it might need. From there: prohibiting optional sharing in regulated source contracts, reconciling scope refusal and source lock ordering, validating quote amounts before gateway confirmation, keeping request decisions out of creation replay identity, invalidating payment sessions on currency changes, and preparing canonical declaration reference envelopes. The orders layer reflected all of that: closing checkout customer snapshots and tenant references, closing address snapshot schemas, validating checkout payment and refund snapshots, binding payment snapshot source inventory with installation guards, qualifying customer fixtures for checkout schema composition, aligning address projection fixtures with checkout schemas, retaining pricing metadata in payment projection fixtures, enforcing checkout line item snapshot schemas, scoping the permissive address fixture to imported lines only, and rejecting explicit null checkout line lists. The null checkout line list rejection is the kind of guard that looks obvious in retrospect but tends to get skipped when you're focused on the happy path. I hit it during fixture work when the schema composition produced an ambiguous result with a missing key versus an explicit null, and the distinction turned out to matter for how the downstream projection handles absence.

The compliance, privacy, billing, MCP, DSR, and agent surface work was lower volume per area but collectively covered real ground. Compliance got physical category authority requirements, authority controls that stay active without proof output, sealed category authority publication receipts, exact current processing purpose authority resolution, evidence time and census deadline enforcement, checkout element assignment evidence requirements, actual export scope bounding, and simplified suppression export attempt validation. The whitespace preservation requirement sounds trivial but isn't — raw composition receipts feed into audit chains, and a formatting change that looks like a no-op can break receipt comparison at verification time. Billing resolved a tax-blocked reconciliation through a native worker, measured native retry action coverage, verified completed redelivery acknowledgment, bound booking review to its committed plan change, exercised duplicate captured booking review deliveries, and asserted current missing-account queue refusal. The MCP work produced two things worth noting: signing execution receipt payloads with tenant-bound Ed25519 custody, and binding native discovery to current authority with audit ownership retention. The Ed25519 binding gives future audit verification a chain it can walk without trusting intermediary claims. On the agent surface, I decided delegated cross-tenant execution semantics and added a signed end-to-end test to prove them — that's the `esp-xtenant-decision` unit, and the decision itself is that delegated execution inherits the originating tenant's authority envelope rather than acquiring the target tenant's. The signed test locks that in as a contract, not just a convention.
