## Today's Update

Today was a full structural remediation session — the kind where the goal isn't shipping a feature but establishing the contracts that make future features safe to write. Almost everything touched the `platform-state-machine-remediation-20261016` feature set, and that work was dense enough that the cross-cutting items in commerce, email, approvals, and elsewhere almost feel like footnotes by comparison. They're not, but that's how the day weighted out.

The remediation work broke into four distinct problem surfaces, each of which required its own design sequence before implementation made sense. The first was deployment readiness — specifically, the gap between what the staging gate accepts and what the production gate should require. Staging was accepting HTTP 200 responses as proof of success without parsing whether the response body actually indicated readiness, which means the gate was passing jobs that hadn't fully settled. I reproduced that false acceptance in fixtures, then aligned the production gate to require genuine public readiness rather than an optimistic status code. The recovery path for post-apply failures got documented in the same pass. The second surface was the customer points ledger, where the core problem was concurrent debit writers operating without serialization. I enumerated all the debit writer paths first — redemption, FIFO expiration, authorized negative corrections — then established a shared lock before reworking each path to operate under it. Testing that properly meant writing concurrent contention tests at both READ COMMITTED and REPEATABLE READ isolation levels, plus a separate expiration-against-redemption race, a correction-against-redemption race, and a tenant scope rollback test. The isolation level tests in particular are the kind of thing that's easy to skip and painful to discover missing later, when actual concurrent writes reveal behavior that the single-threaded test path never exercised.

The Shopify delivery thread was about generation fencing — making sure that failure and completion callbacks from an older delivery attempt can't settle against state that a newer attempt already owns. That required persisting the delivery generation in the schema, capturing it at job admission, binding the redrive to a new generation increment, and then fencing both the failure and completion handlers so stale callbacks are recognized and refused. The existing-state recovery path got prepared in the same pass. The approval evidence thread addressed durability and boundary enforcement: required generic approval evidence now persists atomically rather than being reconstructed at decision time, orphan approval detection and recovery logic is in place, and the system now refuses owner-specific generic approval mutations that would otherwise bypass the domain review path. Testing the HTTP refusal, the legitimate ChangeSet review path, and the evidence failure cases closed the loop on that surface.

Woven through all of this was idempotent replay identity work on two separate paths. Redemption commands now carry an immutable intent identifier stored at admission, which means fast replays can validate against the original intent rather than re-deriving it — and when a unique collision surfaces during a race, the recovery path validates intent against the stored record rather than treating the collision as a clean retry. The DSR command path got the same treatment: governed command identity is now persisted and enforced under the points lock on replay, with a historical identity review path available for reconciliation. The distinction between "this is a replay of the same command" and "this is a new command that happens to collide" is the kind of design question that only becomes urgent when you're operating with real concurrency and real lock contention, but the cost of retrofitting identity after the fact is high enough that establishing it now is clearly worth it.

The cross-cutting work — email settlement suite, approvals worker handshake records, MCP receipt endpoints under their owning tenants, loyalty ledger serialization, DSR replay binding, privacy import proposal digest scoping, bookings unverified stored-value tender rejection — each addressed a specific contract that needs to hold before the surrounding feature area can be built out safely. The email settlement work in particular took several passes: getting the MySQL settlement suite scoped to what the native cohort doesn't already cover, using the runner's default budget for the cohort rather than a custom one, then narrowing again once the measured cohort time was recorded. Three revisions to get that boundary right isn't unusual when the cohort itself is being defined for the first time, but it's worth noting that the final scope is materially different from where I started. Whether I drew the boundary in the right place is something the next suite extension will tell me.

Gate 1 evidence records are now in place for all four major remediation surfaces — readiness, points, Shopify delivery, and approvals — and the in-progress items are in reconciliation. The next step is moving into the ownership and evidence scope reviews that will determine whether the remediation work as a whole is ready for the second gate review.
